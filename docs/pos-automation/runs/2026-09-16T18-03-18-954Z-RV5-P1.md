## Alcance publicado en este checkpoint

La ruta `POST /api/pos/tickets/:id/revisions` sólo registraba un `Record<string, unknown>` en `PosTicketEvent`, consumía la autorización y aumentaba la versión. El renderer anunciaba explícitamente que el original no había sido alterado. Este checkpoint materializa el subconjunto seguro de tickets minoristas sin adeudos, membresías, citas, paquetes/cortesías ni participación comercial de empresa:

1. `PosTicketRevisionRequestDto` y `posTicketRevisionRequestSchema` describen clienta, vendedores, productos, descuento, estado/importe de pago y pagos con decimales exactos. El schema es estricto, concilia `amountPaid` con el detalle y continúa rechazando PAN/CVV/banda.
2. El servicio bloquea la fila del ticket, vuelve a cotizar con catálogo y reglas vigentes, valida vendedor/sucursal y pago, y sólo después consume el token master. Todo corre dentro de `executePosIdempotent`; un error revierte autorización y efectos.
3. Los cobros originales no se reescriben: se agrega `REFUND` por el estado efectivo anterior y `REVISION` por el nuevo. Ambos generan `Venta`, `VentaDetalle` y `PosLegacySaleProjection` compensatorias mediante el motor existente.
4. Las cantidades físicas se comparan por producto. El delta se aplica mediante `createInventoryLedgerMovement` como `COUNT_ADJUSTMENT`, con actor, terminal, fecha, ticket y versión.
5. El `PosTicketEvent` inmutable guarda esquema 1, versión aplicada, estado antes/después, diferencias y los IDs de compensación, nuevo cobro y movimiento. La relación existente conserva actor y autorización. `PosTicket` mantiene el resumen efectivo, mientras líneas, cobros y proyecciones originales permanecen append-only.
6. `ticketDto` usa la última revisión aplicada para lista, detalle y bootstrap: clienta, importes, líneas, vendedores y cobro efectivo reaparecen después de recargar. El renderer vuelve a consultar el ticket tras guardar y sólo entonces confirma que fue aplicado.

No se añadió pantalla, campo, modal ni estilo. El diálogo aprobado sigue mostrando los mismos controles y `Guardar y actualizar registros`; sólo cambió su contrato y resultado persistido.

## Límites seguros de este checkpoint

Para no publicar proyecciones cruzadas incompletas, el servidor devuelve `409` antes de consumir la autorización cuando una revisión cambiaría:

- productos con adeudos o entregas pendientes/históricas;
- líneas, clienta o vendedores de un ticket con membresías;
- líneas, clienta o vendedores de un ticket con citas/Agenda;
- un ticket con participante comercial `COMPANY`.
- paquetes o líneas de cortesía, cuyos contratos no viajan completos en el diálogo.

Esos casos forman el siguiente checkpoint RV5-P1. El check del plan permanece abierto porque aún faltan sus compensaciones, saldos y pruebas de reportes. No se reinterpretó este avance parcial como aceptación completa.
