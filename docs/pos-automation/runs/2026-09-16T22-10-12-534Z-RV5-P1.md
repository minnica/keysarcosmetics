## Alcance de este checkpoint

Este checkpoint materializa el caso de adeudos repetidos que sí puede identificarse desde las filas ya aprobadas del diálogo:

1. El adaptador de ticket ya expone `backendLineId` en cada producto. `TicketEditDialog` conserva esa identidad internamente como `ticketLineId` y la devuelve al guardar; `App.tsx` la transmite como campo opcional del contrato estricto. No aparece un control nuevo y las filas agregadas aún no persistidas no inventan un ID.
2. La transacción valida antes de consumir autorización que los IDs enviados no estén repetidos, pertenezcan al ticket y, para paquetes/cortesías, coincidan con la fila protegida en la misma posición.
3. La nueva proyección conserva el ID de toda fila identificada. Si un artículo aparece varias veces, cada `PosOwedProduct` se concilia únicamente contra la línea vigente/revisada con el mismo `ticketLineId`; una identidad compartida o perdida continúa en `409`.
4. Se mantiene la semántica anterior de entrega e inventario: nunca se reduce por debajo de lo entregado, el historial no se reescribe y el ledger representa sólo unidades físicamente comprometidas.

RV5-P1 permanece abierto: no se implementaron altas, bajas, sustituciones o efectos externos que el diálogo no identifica inequívocamente.
