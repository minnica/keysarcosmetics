## Resultado

Se implementó y probó un provisionador POS opt-in que carga un conjunto sintético completo sólo en una PostgreSQL local dedicada. El dataset cubre sucursal/perfiles, puestos, empleados, usuarios, credenciales master y operador con permisos diferentes, catálogo publicado, precios, inventario de sucursal y bodega, clientas, métodos de pago, banco/redes/MSI, membresía, cortesías y Scheduler interno con disponibilidad real.

El cierre no depende de fixtures del renderer: los datos quedaron persistidos en PostgreSQL y se validaron tanto con Prisma como mediante login y lecturas HTTP reales del API. No se ejecutó `prisma db seed`, el seed general ni una mutación sobre una BD compartida. No se cargaron credenciales operativas y no se atribuyó aprobación al PO.

## Guardas y secretos

El helper falla antes de mutar si no se cumplen todas estas condiciones:

1. `POS_DEMO_CONFIRMATION=LOCAL_SYNTHETIC_ONLY`.
2. `POS_DEMO_DATASET_ID` explícito y válido.
3. `DATABASE_URL` y `DIRECT_URL` coincidentes, PostgreSQL, host `127.0.0.1`/`localhost`/`::1`, base `keysar_pos_demo` o `keysar_pos_demo_<sufijo>` y usuario dedicado distinto de `postgres`.
4. `POS_DEMO_CREDENTIALS_FILE` resuelto dentro de `.pos-runner/`.
5. Conexión efectiva al nombre, usuario y schema `public` esperados.
6. Base sin datos operativos previos, salvo que ya contenga el marcador auditable del mismo dataset.

En `provision`, PIN, contraseñas y secreto de terminal se generan localmente y sólo se guardan en el JSON indicado con modo `0600`; la salida contiene cantidades y ruta relativa, nunca valores. El helper reutiliza `hashPosSecret`, `verifyPosSecret`, `fingerprintSecret`, normalizadores POS, el árbol migrado de permisos, la bodega canónica `pos-loc-matrix` y los catálogos canónicos de bancos, Visa/Mastercard y MSI.

La carga completa usa una transacción de Prisma. El marcador `POS_SYNTHETIC_DATASET_PROVISIONED` sólo se escribe al terminar. Una falla no deja altas parciales, y la reentrada no modifica `PosMembershipTerms` ni versiones de cortesía append-only.

## Comandos para continuar

Con el entorno local dedicado activo y sin imprimir los valores de `config.env`:

```bash
set -a
source "$PWD/.pos-runner/rv10-p2-local/config.env"
set +a
pos_demo_url="postgresql://keysar_pos_demo:${POS_DEMO_DB_PASSWORD}@127.0.0.1:55471/keysar_pos_demo?schema=public"

POS_DEMO_CONFIRMATION=LOCAL_SYNTHETIC_ONLY \
POS_DEMO_DATASET_ID=rv10-p2 \
POS_DEMO_CREDENTIALS_FILE="$PWD/.pos-runner/rv10-p2-local/credentials.json" \
DATABASE_URL="$pos_demo_url" DIRECT_URL="$pos_demo_url" \
POS_PIN_PEPPER="$POS_DEMO_POS_PIN_PEPPER" \
POS_JWT_SECRET="$POS_DEMO_POS_JWT_SECRET" \
pnpm --dir backend/api exec tsx scripts/provision-pos-local-demo.ts verify
```

Para otro candidato o dataset, usar un state dir, contenedor, puertos, base y archivo de credenciales nuevos. Nunca copiar el JSON al renderer, al repositorio, a un informe o a un canal público.
